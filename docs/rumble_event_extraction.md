# 模拟器事件提取与手柄震动方案

## 结论

DIJI-NES 可以从模拟器内部提取一些底层事件，用来驱动 ESP-NOW 手柄震动，但需要区分“通用启发式事件”和“游戏语义事件”。

通用事件适合先做，可以覆盖所有 ROM，但它只能推断“像是音效/碰撞/爆炸”。游戏语义事件更准确，比如受伤、死亡、吃道具，但必须按具体 ROM 做适配。

## 当前代码里的可用入口

- CPU 总线写入入口：`src/nes.cpp` 的 `NES::cpuWrite()`。
  - CPU RAM 写入在 `$0000-$1FFF`。
  - APU 寄存器写入在 `$4000-$401F`，会转发到 `apu.regWrite(addr, val)`。
- APU 寄存器入口：`src/apu.cpp` 的 `APU::regWrite()`。
  - `$4000-$4003`：脉冲波 1。
  - `$4004-$4007`：脉冲波 2。
  - `$4008-$400B`：三角波。
  - `$400C-$400F`：噪声通道。
  - `$4015`：通道启用状态。
- PPU 帧状态：`src/ppu.h` 有 `frameReady` 等渲染状态，但它更适合显示同步，不适合直接判断游戏事件。
- ESP-NOW 协议：`src/espnow_gamepad_protocol.h` 的 v2 `Rumble` 包已包含序号、强度和时长；主机发送接口与手柄非阻塞 PWM 驱动均已实现。

## 方案 A：APU 音效启发式震动

这是推荐的第一阶段方案。

实现思路：

- 在 APU 写寄存器时监听音效特征，优先关注噪声通道 `$400C/$400E/$400F`。
- 噪声通道常被 NES 游戏用于爆炸、碰撞、枪声、受击、鼓点等声音。
- 检测到短促且强度较高的音效后，生成一个短震动请求。
- 震动请求不要在 APU 内直接发送 ESP-NOW，只记录事件或入队，由主循环统一发送。
- 必须加入冷却时间，例如 80-150ms，避免音乐鼓点或连续音效导致一直震。

优点：

- 不需要知道具体游戏。
- 所有 ROM 都能有基础震动反馈。
- 接入点清晰，改动范围小。

缺点：

- 不是游戏真实语义，可能把音乐里的鼓点当成震动。
- 不同游戏音效写法不同，需要调阈值。
- 只能做“增强反馈”，不能保证精确表示受伤或爆炸。

## 方案 B：CPU RAM Watchpoint 游戏适配

这是第二阶段方案，适合常玩的游戏逐个优化。

实现思路：

- 根据 ROM 名称或 ROM 哈希加载事件配置。
- 在 `NES::cpuWrite()` 的 RAM 写入路径里监听指定地址变化。
- 配置里定义地址、变化条件和震动效果。
- 例如某个游戏的生命值地址减少时震动，死亡状态地址变化时长震。

优点：

- 事件准确，可以做出“受伤、死亡、开枪、爆炸”等语义反馈。
- 不容易被背景音乐误触发。

缺点：

- 每个游戏都要单独找地址。
- 不同版本 ROM 地址可能不同，最好用 ROM 哈希匹配。
- 需要一套小型配置系统。

## 方案 C：PPU/OAM 图像启发式

暂不推荐作为主方案。

PPU 和 OAM 可以观察精灵、画面变化、Sprite 0 Hit 等底层状态，但它们很难稳定对应到“玩家被打中”这类语义。不同游戏精灵布局差异很大，误判概率高，性能成本也更难控制。

## ESP-NOW 震动链路建议

主机端：

- 扩展 `DijiEspNowGamepadPacket`，增加震动强度和时长字段。
- 新增 `espNowHostSendRumble(player, strength, durationMs)`。
- 支持 P1/P2 独立发送震动。
- 事件检测模块只生成震动请求，ESP-NOW 发送在主循环中节流处理。

手柄端：

- 增加马达 GPIO 配置。
- 收到 `Rumble` 包后按强度和时长驱动马达。
- 支持覆盖或延长当前震动，避免包太多导致状态混乱。

硬件注意：

- ESP32-C3 GPIO 不应直接驱动震动马达。
- 建议使用三极管或 MOSFET 做开关，马达两端加续流二极管。
- 如果马达电流较大，应独立供电并共地。
- 如果需要强度控制，选择支持 PWM 的 GPIO。

5. 后续在设置中提供震动开关和全局强度。
